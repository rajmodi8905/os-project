The Master Key

The bug we only found by testing: the kernel itself can crash on a page we just protected

A courier with a master key

A building courier carries a master key that opens every door. A "Do Not Enter" sign is on one room. A careless courier uses the master key anyway, walks in, and trips the alarm for the whole building.

The {{kernel}} is that courier. When a program asks it to copy data into a {{buffer}}, the kernel does the writing. If that buffer is on a protected page, the kernel is the one who hits the glass.

⚠️
We reproduced this crash before fixing it

A test that called read() from a pipe into a protected page brought down the whole guest. This is the real output.

The CPU raised trap 14, a {{page fault}}, but this time the code running was the kernel, not a user program.

xv6 treats any kernel-mode fault as a kernel bug and calls {{panic|panic}}. The whole machine stops.

Why the kernel is not exempt

xv6 sets a CPU switch called {{CR0.WP|CR0.WP}} when it boots. With it on, even kernel code must respect read-only pages.

@@TB:entry.S:53:56@@

A note: turn on paging.

Read the control register 0 into a working register.

Set two bits: PG (use page tables) and WP (write-protect: the kernel obeys read-only pages too).

Write it back to the CPU. From now on the kernel needs permission like everyone else.

@@/TB@@

The fix, in four small pieces

First the checker itself. It walks every page the buffer touches, so a buffer that starts on a writable page and runs onto a protected one is caught too.

@@TB:vm.c:367:376@@

A length of zero means nothing will be written, so there is nothing to check.

(the return for that case)

Find the page that holds the last byte of the buffer.

Loop from the first page to that last page, one page at a time.

Look up each page's table entry. Never create one while checking.

All three flags must be set: present, user, writable. Anything less is refused with -1.

(the refusal)

After the last page, stop. Without this the loop would run on forever.

(the exit)

End of the loop. Every page passed.

@@/TB@@

Then a thin wrapper that adds the check to the existing bounds test.

@@TB:syscall.c:74:80@@

A new helper next to the old argptr.

Its name says it all: "argument pointer, writable".

(open brace)

First do the old check: is the buffer even inside the process? If not, fail.

(the failure)

Then run the new check on the same buffer and return its answer.

(close brace)

@@/TB@@

Three callers changed by exactly one word each: argptr became argptrw.

@@TB:sysfile.c:76:78@@

In sys_read: get the file, the length, and the buffer, and now require the buffer to be writable. The same one-word change was made in sys_fstat (line 112) and sys_pipe (line 429).

If any of that fails, return -1 without touching anything.

Only now do the real work of reading into the buffer.

@@/TB@@

One more backdoor. copyout writes through the kernel's own mapping of the page, which is always writable, so it would bypass the user's protection.

If there is none, fail.

Our one added line: the user's mapping must also be writable.

Otherwise refuse.

Safe here, not everywhere

Checking and then writing is safe because xv6 here has one CPU and no threads, so nothing can change the page in between. A multi-CPU kernel would need a {{lock}}, or a way to survive the fault.
