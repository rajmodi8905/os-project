The Case File

The assignment, the problem in the original xv6, how we solved it, what surprised us on the way, and how we know it works

A patient walks in

A doctor's case file always has four parts: the symptom, the diagnosis, the treatment, and the outcome. This whole project fits that shape, so we will open it first and fill in the details in the modules that follow.

🩺
Symptom

In the original {{xv6}}, a program can write to any page it owns. There is no way to say "this part must never change".

🔍
Diagnosis

The hardware already has a permission bit for this. The kernel simply never lets a program use it.

💊
Treatment

Two new system calls, mprotect and munprotect, plus the guard rails that make them safe.

✅
Outcome

65 checks pass, the original xv6 tests still pass, and a live demo shows a blocked write.

The assignment

This is an individual operating-systems course project. It comes from the {{OSTEP}} virtual-memory project, the "read-only code" part, done in the x86 version of xv6.

🎯

What we had to build

Let a program remove write permission from its own pages, keep reading them, and restore write permission later.

🧱

What we started from

The unchanged x86 xv6 source, pinned at one exact commit, building and booting in {{QEMU}} with its own tests passing.

🚫

What we left out

Protecting address 0 (null pointers), swapping, copy-on-write and threads. A smaller scope, done properly.

🎓
The rules of the viva

The change is small. The hard part is making it safe.

How it was built, step by step

The work followed a plan with checkpoints. The real history is in the repository; this is the story of it.

1
Baseline first

Pin the original xv6, add one-command build, run and check scripts, and get a green CI run. Nothing new yet.

2
The two system calls and the helper

Wire up numbers 22 and 23 and write setuvmwrite with its validate-then-change structure. First tiny test: protect, read, refused write, restore.

3
A crash we did not plan for

A test that read from a pipe into a protected page panicked the whole kernel. We reproduced it first, then added the writable check. Module 6.

4
The full test suite, and a gap in it

We deleted the CR3 reload on purpose. The suite still passed. So we added the test that catches it. Module 7.

5
A demo and the explanations

A friendly demo program, then the documents that map every changed file. This course is the last piece.

6
Check it somewhere else

The same check passed in GitHub Actions and on a fresh clone on a Linux laptop. A second machine finds what the first one hides.

💡
Two bugs were found by testing, not by thinking

The kernel crash and the missing-flush gap were both discovered because we tried to break our own work. Good engineering is mostly arranging for your mistakes to show up early.
