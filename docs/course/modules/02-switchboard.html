The Switchboard

Meet the six characters a single mprotect call passes through, and the files each one lives in

An old office switchboard

Picture a company with one front-desk operator and a board of numbered extensions. A caller says "extension 22, please". The operator plugs the cable into slot 22 and a specialist picks up.

A system call works the same way. Your program asks for a numbered service, and the kernel connects it to the right handler.

📞
Your program

Calls mprotect(p, 2) like any normal function.

🔔
The stub, usys.S

Writes the extension number (22) on a note and rings the kernel's bell.

🔀
The switchboard, syscall.c

Reads the number and plugs into the matching slot of the dispatch table.

🗒️
The receptionist, sysproc.c

Collects the details (address, count) and passes them on. Adds no rules.

🛠️
The specialist, vm.c

The function setuvmwrite does the real work on the page table.

Or listen to them talk

The same journey as a group chat. Each character only knows its own job.

P
Program

Hello kernel! Please make 2 pages starting at p read-only.

S
Stub

I only do one thing: write 22 in EAX and ring the bell. int T_SYSCALL!

D
Switchboard

22? That is sys_mprotect. Connecting you now. If it were 99 I would print "unknown sys call".

R
Receptionist

Got it: address and count from the user stack. Same form for munprotect, only the last box changes. Over to the specialist.

V
Specialist

First I check every page: aligned, mapped, user-owned. Nothing is touched until all pass.

V
Specialist

All good. Clearing the write bit on both pages, then reloading CR3 so the CPU forgets the old cache.

R
Receptionist

Result is 0. Passing it back up.

P
Program

Zero means success. Now I will try to write to p... and see what the CPU says.

The wiring, in real code

These four small pieces are the entire path. Everything else in xv6 is untouched.

CODE · usys.S · lines 4-9 
#define SYSCALL(name) \
  .globl name; \
  name: \
    movl $SYS_ ## name, %eax; \
    int $T_SYSCALL; \
    ret
PLAIN ENGLISH

A template called SYSCALL that builds one tiny function per system call.

Make that function visible to the rest of the program.

Put this call's number into the EAX register. We added numbers 22 and 23.

Knock on the kernel door with a software interrupt.

When the kernel finishes, return to the program with whatever it left in EAX.

PLAIN ENGLISH

Slot 22 of the table holds the handler for mprotect.

Slot 23 holds the handler for munprotect. Our only table edits.

PLAIN ENGLISH

Read the call number the stub left in EAX.

Check it is a real slot with a real handler, otherwise print "unknown sys call".

Run the handler and store its answer back in EAX, which is what the program sees as the return value.

CODE · sysproc.c · lines 96-105 
static int
changeprotection(int writable)
{
  int addr, len;
  struct proc *curproc = myproc();
 
  if(argint(0, &addr) < 0 || argint(1, &len) < 0)
    return -1;
  return setuvmwrite(curproc->pgdir, curproc->sz, (uint)addr, len, writable);
}
PLAIN ENGLISH

A private helper shared by both calls. writable is 0 for mprotect and 1 for munprotect.

Find the process that made the call.

Fetch argument 0 (the address) and argument 1 (the page count) from the user's stack. If that fails, return -1.

Hand everything to setuvmwrite: page directory, process size, address, count, wanted state.

That single return is the whole body. The receptionist adds no rules of its own.

🧩
One helper, two thin wrappers

mprotect and munprotect call the same function with a different last argument. That keeps their rules identical, so they can never drift apart.
