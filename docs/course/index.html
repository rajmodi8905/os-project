How xv6 Locks a Page
01

The Glass Case

What happens when a program locks part of its own memory, and why that is harder than flipping one switch

Look, but do not touch

Think of a museum display case. Everyone can see what is inside, but the glass stops anyone reaching in. Our project builds that glass for a program's own memory.

A program calls mprotect on a few pages. From then on it can still read them. The moment anything tries to write, the hardware slams shut.

🔒

mprotect(addr, len)

Put glass over len pages starting at addr. Reads still work, writes are refused.

🔓

munprotect(addr, len)

Take the glass off again. The pages are writable as before.

📏

len counts pages

Not bytes. One page is 4096 bytes, and addr must start exactly on a page boundary.

Watch it happen, for real

This is the real output of the demo program vmdemo 7 3, run inside the xv6 guest. Read it top to bottom.

REAL OUTPUT · guest_output.txt · lines 3-10 
[1] 3 page(s) at 0x4000, writable control
      stored and read back 7 ... 9
 
[2] mprotect(0x4000, 3) = 0
      protected read still works: 7
pid 4 vmdemo: trap 14 err 7 on cpu 0 eip 0x2ed addr 0x6000--kill proc
      child write of 107 to 0x6000: STOPPED by page fault (child killed)
      parent still alive, value unchanged: 9
PLAIN ENGLISH

Scene 1: three pages are writable. The program stores 7, 8, 9 and reads them back.

Scene 2: mprotect returned 0, meaning success. Reading still works: you can look through the glass.

A child process now tries to write. The CPU raises trap 14 err 7: a write to a protected page.

That child is killed. Only the one who touched the glass.

The parent is untouched. 9 is still 9.

That last line is the whole point: a protected write must hurt only the program that tried it.

💡
Permission belongs to a whole page

The hardware cannot protect 100 bytes in the middle of a page. It only knows pages. So everything on the same page shares one fate.

Six rules that make it hard

Flipping one bit sounds easy. These six rules are what the rest of the course is about.

1
Reads must still work

Clear only the write bit, nothing else. Module 3.

2
A write kills only that process

The system keeps running. Modules 3 and 6.

3
A failed call changes nothing

No half-protected ranges. Module 4.

4
The change is immediate

The CPU keeps a cache that can still say "writable". Module 4.

5
Protection survives fork

The child copy is protected too, and independent. Module 4.

6
The kernel must not be fooled

Asking the kernel to write into your protected page must not crash it. Module 5.

Out of scope: protecting address 0 (null pointers), swapping, copy-on-write, and threads.

Key Cards

How an address becomes a page, and the three permission bits the hardware checks every time you touch memory

A hotel with floors, rooms and key cards

To find your bed you need a floor, a room on that floor, and a spot inside the room. A 32-bit virtual address is split the same way: a floor number (10 bits), a room number (10 bits), and a spot inside the room (12 bits).

Each room has a lock record with permissions. That record is what we are about to edit. Type an address and watch it split.

The real macros that do the splitting

These macros come straight from mmu.h, the file that defines the hardware's layout for xv6.

CODE · mmu.h · lines 73-77 
// page directory index
#define PDX(va)         (((uint)(va) >> PDXSHIFT) & 0x3FF)
 
// page table index
#define PTX(va)         (((uint)(va) >> PTXSHIFT) & 0x3FF)
PLAIN ENGLISH

A label: the next macro finds the floor.

PDX: shift the address right by 22 bits and keep 10 bits. That is the directory index.

Another label: now the room.

PTX: shift right by 12 bits and keep 10 bits. That is the page table index.

CODE · mmu.h · lines 85-91 
#define PGSIZE          4096    // bytes mapped by a page
 
#define PTXSHIFT        12      // offset of PTX in a linear address
#define PDXSHIFT        22      // offset of PDX in a linear address
 
#define PGROUNDUP(sz)  (((sz)+PGSIZE-1) & ~(PGSIZE-1))
#define PGROUNDDOWN(a) (((a)) & ~(PGSIZE-1))
PLAIN ENGLISH

A page is 4096 bytes. The whole project is built on this number.

The two shift distances used above.

PGROUNDUP: round an address up to the next page start.

PGROUNDDOWN: clear the low 12 bits to find the start of the page an address is on.

💡
Page number and offset are just division

page number = address / 4096, and offset = address % 4096. Because 4096 is 2 to the power 12, "divide" means "drop the low 12 bits".

The key card: three bits we care about

The PTE stores the physical page in its top 20 bits and the permission bits in its low 12. We use three. The orange one is our entire project.

CODE · mmu.h · lines 93-101 
// Page table/directory entry flags.
#define PTE_P           0x001   // Present
#define PTE_W           0x002   // Writeable
#define PTE_U           0x004   // User
#define PTE_PS          0x080   // Page Size
 
// Address in page table or page directory entry
#define PTE_ADDR(pte)   ((uint)(pte) & ~0xFFF)
#define PTE_FLAGS(pte)  ((uint)(pte) &  0xFFF)
PLAIN ENGLISH

The permission flags that live in the low 12 bits of every entry.

P (present): the room exists and is mapped.

W (writable): guests may rearrange the furniture. Our project toggles this bit.

U (user): ordinary programs may enter, not just the kernel.

A flag xv6 uses for big pages. We never touch it.

Two more labels.

PTE_ADDR: keep the top 20 bits, which are the physical page.

PTE_FLAGS: keep the low 12 bits, which are the permissions.

Block 1: turn away the obviously wrong

CODE · vm.c · lines 325-326 
  if(va % PGSIZE != 0 || npages <= 0 || va >= sz)
    return -1;
PLAIN ENGLISH

Reject the request if: the start is not on a page boundary, the count is zero or negative, or the start is already past the end of the process.

Return -1. Nothing has been touched yet, so "failed" really does mean "unchanged".

Because npages is a signed int, a negative count is caught by the same test.

Block 2: count first, multiply never (until it is safe)

The obvious check is "start plus count times 4096 must be inside the process". It has a trap. Play with it below.

CODE · vm.c · lines 327-331 
  // Compare page counts instead of computing va + npages*PGSIZE first,
  // so a large npages cannot overflow past the check.
  if((uint)npages > (sz - va) / PGSIZE)
    return -1;
  end = va + (uint)npages * PGSIZE;
PLAIN ENGLISH

A note from the author: compare page counts instead of computing the end address first.

The reason: the multiplication could overflow 32 bits and wrap to a small number.

How many whole pages fit between the start and the end of the process? If the request is bigger than that, reject it.

Return -1.

Only now is it safe to compute the end address, because we know it lies inside the process.

Block 3: pass one, inspect every page

CODE · vm.c · lines 333-339 
  // Pass 1: every page must already be a present user page.
  // The stack guard page has PTE_U cleared and is rejected here.
  for(a = va; a < end; a += PGSIZE){
    pte = walkpgdir(pgdir, (void*)a, 0);  // never allocates
    if(pte == 0 || (*pte & PTE_P) == 0 || (*pte & PTE_U) == 0)
      return -1;
  }
PLAIN ENGLISH

A note: every page must already be present and owned by the user.

The guard page below the stack has its user bit cleared, so it will fail the test below.

Visit each page in the range, one page-size step at a time.

Look up its table entry. The 0 means "never create a page table while only checking".

If there is no entry, or it is not present, or it is not a user page...

...turn the whole request away. We have changed nothing yet.

End of the inspection loop. Everyone passed.

The Master Key

The bug we only found by testing: the kernel itself can crash on a page we just protected

A courier with a master key

A building courier carries a master key that opens every door. A "Do Not Enter" sign is on one room. A careless courier uses the master key anyway, walks in, and trips the alarm for the whole building.

The kernel is that courier. When a program asks it to copy data into a buffer, the kernel does the writing. If that buffer is on a protected page, the kernel is the one who hits the glass.

⚠️
We reproduced this crash before fixing it

A test that called read() from a pipe into a protected page brought down the whole guest. This is the real output.

REAL OUTPUT · panic_output.txt · lines 1-2 
unexpected trap 14 from cpu 0 eip 80103743 (cr2=0x5000)
lapicid 0: panic: trap
PLAIN ENGLISH

The CPU raised trap 14, a page fault, but this time the code running was the kernel, not a user program.

xv6 treats any kernel-mode fault as a kernel bug and calls panic. The whole machine stops.

Why the kernel is not exempt

xv6 sets a CPU switch called CR0.WP when it boots. With it on, even kernel code must respect read-only pages.

CODE · entry.S · lines 53-56 
  # Turn on paging.
  movl    %cr0, %eax
  orl     $(CR0_PG|CR0_WP), %eax
  movl    %eax, %cr0
PLAIN ENGLISH

A note: turn on paging.

Read the control register 0 into a working register.

Set two bits: PG (use page tables) and WP (write-protect: the kernel obeys read-only pages too).

Write it back to the CPU. From now on the kernel needs permission like everyone else.

The fix, in four small pieces

First the checker itself. It walks every page the buffer touches, so a buffer that starts on a writable page and runs onto a protected one is caught too.

CODE · vm.c · lines 367-376 
  if(len == 0)
    return 0;
  last = PGROUNDDOWN(va + len - 1);
  for(a = PGROUNDDOWN(va); ; a += PGSIZE){
    pte = walkpgdir(pgdir, (void*)a, 0);
    if(pte == 0 || (*pte & (PTE_P|PTE_U|PTE_W)) != (PTE_P|PTE_U|PTE_W))
      return -1;
    if(a == last)
      break;
  }
PLAIN ENGLISH

A length of zero means nothing will be written, so there is nothing to check.

Find the page that holds the last byte of the buffer.

Loop from the first page to that last page, one page at a time.

Look up each page's table entry. Never create one while checking.

All three flags must be set: present, user, writable. Anything less is refused with -1.

After the last page, stop. Without this the loop would run on forever.

End of the loop. Every page passed.

Then a thin wrapper that adds the check to the existing bounds test.

CODE · syscall.c · lines 74-80

    return -1;

}
PLAIN ENGLISH

A new helper next to the old argptr.

Its name says it all: "argument pointer, writable".

First do the old check: is the buffer even inside the process? If not, fail.

Then run the new check on the same buffer and return its answer.

Three callers changed by exactly one word each: argptr became argptrw.

CODE · sysfile.c · lines 76-78 
  if(argfd(0, 0, &f) < 0 || argint(2, &n) < 0 || argptrw(1, &p, n) < 0)
    return -1;

In sys_read: get the file, the length, and the buffer, and now require the buffer to be writable. The same one-word change was made in sys_fstat (line 112) and sys_pipe (line 429).

If any of that fails, return -1 without touching anything.

Only now do the real work of reading into the buffer.

  if(pid == 0){

PLAIN ENGLISH

We are the child. A fault here kills only us.

Close the read end of the pipe; the child only writes.

Print which address we are about to write, for the log.

The write under test.

The marker. We only get here if the write above succeeded.

Leave normally.

End of the child's code.

CODE · vmtest.c · lines 61-67 
  close(fds[1]);
  n = read(fds[0], &marker, 1);
  close(fds[0]);
  wait();
  if(n == 0)
    faults++;
  return n == 0;
PLAIN ENGLISH

Parent: close the write end so end-of-file can arrive.

Read one byte. Zero bytes means the child died before the marker.

(close our read end) then wait for the child to be cleaned up.

If we got zero bytes, the child was stopped...

...so count one more fault. The runner compares this count with the kernel messages later.

Report: 1 means "the write faulted", 0 means "it succeeded".

What the suite proves

65 checks in seven groups, written to catch the six rules from Module 1.

1

basic

Protect, read, a faulting write, restore, write again.

2

immediate

The change is instant. This is the test that needs the CR3 reload.

3

repeated

Calling twice is harmless.

4

multiple

Every page in a range changes; the neighbours do not.

5

forking

The child inherits protection; changes stay independent both ways.

6

invalid

Unaligned, zero, negative, overflow, wrap, past the heap, kernel, guard page: all -1. Mixed ranges change nothing.

7

kernelbuffers

read, fstat, pipe refuse protected buffers; write still works.

The immediate test is the clever one. It writes first, so the CPU caches a writable entry. Then it protects the page and writes again with no process switch in between.

CODE · vmtest.c · lines 101-105 
    *addr = 'a';
    if(mprotect(addr, 1) == 0){
      *addr = 'b';           // must fault here
      write(fds[1], "W", 1);
    }
PLAIN ENGLISH

First write: the CPU now caches "this page is writable".

Protect the page. If this returns 0, continue.

The second write. With CR3 reloaded it faults. Without it, the stale cache lets it through.

The marker: seeing it in the pipe means the protection leaked.

Exercise 1: add getprot(addr)

        
Return 1 if the page holding addr is writable, 0 if read-only, -1 if it is not a valid user page. Use system call number 24.

        
Hint
Copy the wiring of mprotect: syscall.h, syscall.c (extern and table), usys.S, user.h, defs.h. The helper looks up the entry with walkpgdir(…, 0) and tests PTE_W.

        
Answer


  

    CODE · video/examples/getprot_solution.c · lines 6-17
    
int
getuvmprot(pde_t *pgdir, uint sz, uint va)
{
  pte_t *pte;
 
  if(va >= sz)                       // outside the process
    return -1;
  pte = walkpgdir(pgdir, (void*)va, 0);   // 0 = never allocate
  if(pte == 0 || (*pte & PTE_P) == 0 || (*pte & PTE_U) == 0)
    return -1;                       // missing, not present, or kernel page
  return (*pte & PTE_W) ? 1 : 0;     // test the write bit only
}

  

  

    PLAIN ENGLISH
    


The helper in vm.c. Take the page directory, process size and an address.

          
A local variable to hold the table entry.

          
An address outside the process is invalid, so return -1.

          
Look up the entry without creating anything.

          
Missing, not present, or not a user page: also -1.

          
Otherwise answer 1 if the write bit is set and 0 if not.

    

  





  

    CODE · video/examples/getprot_solution.c · lines 20-28
    
int
sys_getprot(void)
{
  int addr;
 
  if(argint(0, &addr) < 0)
    return -1;
  return getuvmprot(myproc()->pgdir, myproc()->sz, (uint)addr);
}

  

  

    PLAIN ENGLISH
    


The system call wrapper in sysproc.c.

          
A variable for the address argument.

          
Fetch argument 0; if that fails return -1.

          
Call the helper with the current process page directory and size.

          
End.

Exercise 2: make len a count of bytes

        
mprotect(p, 5000) should protect two pages (round up). Zero and negative lengths are still invalid.

        
Hint
Only changeprotection() in sysproc.c changes. Convert bytes to pages before calling the helper, and avoid adding 4095 to a number that might be huge.

        
Answer


  

    CODE · video/examples/bytes_solution.c · lines 12-18
    
  if(argint(0, &addr) < 0 || argint(1, &len) < 0)
    return -1;
  if(len <= 0)                    // still reject zero and negative
    return -1;
  len = (len - 1) / PGSIZE + 1;   // bytes -> pages, rounded up
                                  // (never computes len + 4095, so no overflow)
  return setuvmwrite(curproc->pgdir, curproc->sz, (uint)addr, len, writable);

  

  

    PLAIN ENGLISH
    


Fetch the two arguments as before.

          
A length of zero or less is still invalid.

          
Convert bytes to pages, rounding up: subtract one first, divide, add one.

          
The validating helper is unchanged. It now receives a page count.

    

  



          
Which existing tests would now fail? Any that pass a page count such as mprotect(p, 3): they now mean 3 bytes, which is one page.

        

        
      


      

        
Exercise 3: a clearer message on a write fault

        
When a user process writes a read-only page, print pid N name: write to read-only page 0x… before the usual trap line.

        
Hint
It goes in trap.c, in the user-space branch of the default case. Test for trap 14 with the error bits present, write and user.

        
Answer


  

    CODE · video/examples/fault_message_solution.c · lines 7-9
    
    if(tf->trapno == T_PGFLT && (tf->err & 7) == 7)   // present + write + user
      cprintf("pid %d %s: write to read-only page 0x%x\n",
              myproc()->pid, myproc()->name, PGROUNDDOWN(rcr2()));

  

  

    PLAIN ENGLISH
    


Only for a page fault whose error code is "present + write + user" (7). Other faults keep the old message only.

          
Print the process id and name...

          
...and the page that was written, using rcr2() (the faulting address) rounded down to its page.

    

  



          
In the real run above, the output is pid 4 modtest: write to read-only page 0x3000 followed by the usual trap line, and the parent keeps running.

        

        
      


      

        
Exercise 4: refuse page 0, and allow at most 16 pages

        
Hint
Both rules belong in the first check of the shared helper, so they apply to both calls. Only a range that starts at address 0 can include page 0.

        
Answer


  

    CODE · video/examples/limits_solution.c · lines 9-11
    
  if(va % PGSIZE != 0 || npages <= 0 || npages > 16      // cap: at most 16 pages
     || va == 0 || va >= sz)                             // refuse page 0
    return -1;

  

  

    PLAIN ENGLISH
    


Add npages > 16 to the rejection test: the cap.

          
Add va == 0: refuse any range that starts at page 0.

          
Return -1 as before. Nothing has been touched.

    

  



          
Tested in the guest: page 0 is refused, 16 pages work, 17 returns -1, and munprotect obeys the same cap.
