Module 1 of 11

The problem

6 min · requirements table · checkpoint

By the end you can state what the two system calls must do, and the six rules that make this harder than flipping a bit.

In xv6 a process can read and write every page it owns. We add two system calls so a program can switch the write permission of its own pages off and on.

int mprotect(void *addr, int len)

Make len pages, starting at the page-aligned address addr, read-only.

int munprotect(void *addr, int len)

Make those pages writable again. Both return 0 on success and -1 on an invalid request.

len counts pages, not bytes. A page on x86 is 4096 bytes.

Module 2 of 11

Addresses and pages

8 min · interactive: address splitter · checkpoint

By the end you can split any 32-bit address into directory index, table index and offset, and say which page it is in.

A 32-bit virtual address is three fields glued together. The top ten bits pick an entry in the page directory. The next ten bits pick an entry in a page table. The low twelve bits are the offset inside a 4096-byte page.

These are the real macros from mmu.h. PGROUNDDOWN clears the low twelve bits, which is how xv6 finds the start of a page.

Remember

page number = address / 4096, and offset = address % 4096. An address is page-aligned when its offset is 0. Our helper rejects any other start address.

Module 3 of 11

The permission bits

10 min · interactive: PTE lab · checkpoint

By the end you can name the three flags we use, clear only the write bit, and predict what a read or write does.

A page table entry holds the physical page number in its top 20 bits and permission flags in its low 12. We use three flags: PTE_P (the page is present), PTE_W (writes are allowed) and PTE_U (user mode may touch it).

Why this matters

Our whole project is the orange bit. mprotect clears it and munprotect sets it. Every other bit, including the physical page, must stay exactly as it was. That is why we mask with ~PTE_W and never assign the whole entry.

Check the third row with CR0.WP turned off. The kernel would silently write through a read-only page. xv6 sets WP on, so the kernel faults instead. That detail causes a crash in Module 7.

Module 4 of 11

The TLB, write-protect and the fault

10 min · interactive: TLB stepper, error decoder · checkpoint

By the end you can explain why we reload CR3, and decode trap 14 err 7 without looking it up.

The cache that can lie

Walking two page tables on every memory access is slow, so the CPU caches recent translations, together with their permissions, in the TLB. If we change a PTE, the cached copy can be out of date.

Try it

TLB stepper

Writing CR3 flushes the TLB. In setuvmwrite() that is the last real line, lcr3(V2P(pgdir)). You will see it in Module 6. Without it the write in the last step succeeds. We proved this with a test (Module 8).

The kernel also obeys read-only pages

entry.S turns paging on and also sets CR0_WP. With WP set, even kernel-mode writes respect read-only pages.

What a protection fault looks like

When user code writes a read-only page, the CPU raises trap 14, a page fault. This existing handler runs. In user mode it prints a message, marks only that process killed, and returns. In kernel mode it calls panic.

Try it

Error-code decoder

The CPU's error code is three bits. Set them and read the result.

Set all three and you get err 7. That is a user write to a present page that does not allow writes. It is our protection firing. The parent is a different address space, so it keeps running and learns the result through a pipe.

One call, end to end

The program calls mprotect(p, 2). The prototype in user.h lets it compile.

A stub puts the call number in EAX and traps. The macro is shared by every call; ours are the last two lines.

syscall() looks up slot 22. It reads the number from EAX, calls the handler, and writes the return value back into EAX.

sys_mprotect fetches the arguments. Both calls share one front end; only the last argument differs.

setuvmwrite() does the work. It validates, changes the write bit and flushes the TLB. Module 6 takes it apart.

The result returns in EAX. 0 means success, -1 means a bad request. The page table is already changed and the TLB flushed, so the very next write in the program is checked against the new permission.

Module 6 of 11

setuvmwrite, line by line

20 min · interactive: overflow calculator, two-pass simulator · checkpoint

By the end you can rewrite this function from memory and defend each line. It is the heart of the project.

The function takes the page directory, the process size sz, a start address, a page count and the wanted state (writable is 1 for munprotect, 0 for mprotect). Five blocks, in order.

1 · Reject bad arguments

The address must be page-aligned, there must be at least one page, and the start must be inside the process. Because npages is a signed int, negative counts fail here too.

2 · Compare counts, then compute the end

We do not compute va + npages*4096 first, because that can overflow 32 bits. Instead we ask how many whole pages fit between va and sz. Only then is end safe.

3 · Pass one: validate every page

For each page, find the PTE without allocating (0 is the alloc flag). It must exist, be present, and be a user page. The stack guard page has no PTE_U, so it fails here.

4 · Pass two: change only the write bit

This runs only if pass one accepted every page, so it cannot fail halfway. It sets or clears PTE_W and touches nothing else.

5 · Flush the TLB

lcr3 reloads the page-directory register, which empties the TLB. V2P is needed because CR3 takes a physical address and pgdir is a kernel virtual one.

Module 7 of 11

The kernel's blind spot

12 min · interactive: syscall simulator · checkpoint

By the end you can explain the crash we found, why write() is exempt, and what each of the four fixes does.

The bug we reproduced

Before this fix, read() from a pipe into a protected page crashed the guest kernel with unexpected trap 14 ... panic: trap. User code was never the problem. The kernel itself wrote into the page, and WP made that a kernel-mode fault.

Try it

Syscall simulator

The new check walks every page the buffer touches, so a buffer that starts in a writable page and runs into a protected one is also caught.

checkuvmwrite

Length zero is fine. Otherwise find the last page and loop from the first. All three flags, present, user and writable, must be set on every page. It never allocates.

argptrw

The old bounds check first, then this check. One new function, so the three callers stay identical.

The callers

In sys_read, argptr became argptrw. sys_fstat (line 112) and sys_pipe (line 429) changed the same way. sys_write keeps argptr, because it only reads the buffer.

copyout: the backdoor

It writes through the kernel's own mapping of the physical page, which is always writable, so it would bypass the user's read-only mapping. It now checks too. Its only caller is exec, writing a fresh stack, so behaviour is unchanged.

Safe here, not everywhere

Check-then-write is safe because there is one CPU and no threads: nothing can change the page between the check and the write. A multi-CPU kernel would need a lock or fault handling.

Module 8 of 11

Proving it works

15 min · interactive: mutation lab, bug hunt · checkpoint

By the end you can say how a user program detects a fault, what each test group proves, and how we know the tests are real.

How a test sees a fault

A faulting write kills its process, and xv6's wait() returns no exit status. So the child writes a marker byte into a pipe only if the write succeeded. End of file means it died first.

Test groupWhat it proves
basicProtect, read, faulting write, restore, write again
immediateThe change is instant: no stale TLB entry (the CR3 test)
repeatedCalling twice is harmless
multipleAll pages in a range change; neighbours do not
forkingChild inherits; changes are independent both ways
invalidUnaligned, zero, negative, overflow, wrap, past heap, kernel, guard page: all -1; and mixed ranges change nothing
kernelbuffersread, fstat, pipe reject protected buffers; write still allowed

The runner (scripts/smoke.py) goes one step further: the number of faulting children vmtest reports must equal the number of trap 14 err 7 lines the kernel printed. A printed PASS alone is not evidence.
